สถาปัตยกรรม Clean Architecture & โดเมนโมเดล OOP

แยกแกนกลางทางธุรกิจ (Domain Layer) เป็นอิสระจากฐานข้อมูล พร้อมยึดหลัก 4 เสาหลัก OOP

Domain Entities & Value Objects
FloodPoint (Entity) State & Behavior
จุดเฝ้าระวังน้ำท่วม, พิกัด GeoLocation, ระดับน้ำ waterLevel (เมตร) และคำนวณความเสี่ยงผ่าน evaluateRisk(IRiskStrategy)
FloodReport (Entity) Citizen Incident
รายงานจากประชาชน, ระดับความรุนแรง Severity, แนบภาพถ่าย, เบอร์โทร และบันทึกสถานะ PENDING ➔ VERIFIED
GeoLocation (Value Object) Immutable Coords
Encapsulate พิกัดละติจูด/ลองจิจูด พร้อม Invariant Validation ตรวจสอบความถูกต้องของพิกัดในประเทศไทย และคำนวณระยะทาง
Domain Enums & Type Safety 4-Tier Risk
RiskLevel (CRITICAL, HIGH, MEDIUM, LOW), Severity (1-4), และ ReportStatus (PENDING, VERIFIED)
1. Encapsulation (การซ่อนข้อมูลภายใน) GeoLocation และ FloodPoint ซ่อน properties เป็น private มี Validation ภายใน ป้องกันค่าพิกัดผิดพลาด
2. Inheritance (การสืบทอดคุณสมบัติ) FloodVictim (แจ้งเหตุด่วน) และ Traveler (เช็คเส้นทาง) สืบทอดจาก User (Abstract) เพื่อแยกสิทธิ์การทำงาน
3. Polymorphism (พหุสัณฐาน) IRiskStrategy กำหนดเมธอด calculate() โดย CompositeRiskStrategy สลับสูตรคำนวณตามสภาพอากาศได้อิสระ
4. Abstraction (การซ่อนความซับซ้อน) IFloodPointRepository ซ่อนคำสั่ง SQL และ PostGIS ไว้เบื้องหลัง Domain สั่งบันทึกได้โดยไม่ต้องรู้ไส้ในของฐานข้อมูล

3 Design Patterns หลักในการประมวลผลข้อมูล

การประยุกต์ใช้ GoF Patterns เพื่อความยืดหยุ่น การทดสอบ และการประเมินความเสี่ยงอัตโนมัติ

Strategy Pattern
CompositeRiskStrategy

คำนวณคะแนนความเสี่ยงภัยพิบัติแบบถ่วงน้ำหนัก (Weighted Score) อัตโนมัติ:

  • ระดับน้ำ (40%): Water Level 0.1 - 3.0m
  • พยากรณ์ฝน (35%): Rainfall Forecast 3 ชม.
  • ความหนาแน่น (25%): Report Frequency Density
Output ➔ LOW / MEDIUM / HIGH / CRITICAL
Repository Pattern
Supabase / PostGIS Repo

แยก Data Access Layer ออกจาก Domain Logic ตามหลัก Clean Architecture:

  • IFloodPointRepository: บันทึก & คิวรีจุดน้ำท่วม
  • IFloodReportRepository: บันทึกรายงานประชาชน
  • PostGIS Spatial: คิวรีพิกัดเชิงพื้นที่ ST_DWithin
รองรับการสลับไปใช้ Mock ในการทดสอบทันที
Adapter Pattern
External Service Adapters

แปลงโครงสร้างข้อมูลจากภายนอกเข้าสู่มาตรฐานของระบบ:

  • GistdaDisasterService: ดาวเทียม 77 จว.
  • OpenWeatherService: ปริมาณฝนและอากาศ
  • In-Memory Cache (TTL 15m): ตอบสนอง < 30ms
Loose Coupling ไม่ผูกติดกับ SDK ภายนอก

ระบบคำนวณเชิงพื้นที่ & REST API Engine

การคำนวณอาณาเขตน้ำท่วมอัตโนมัติ (Convex Hull) และการเชื่อมต่อข้อมูลความเร็วสูง

Dynamic Flood Polygon Engine
  • Spatial Density Clustering: รวมกลุ่มจุดรายงานที่อยู่ใกล้กัน (< 500 ม.) เกิน 2 รายการ หรือระดับวิกฤต
  • Convex Hull Algorithm: คำนวณจุดยอดรูปหลายเหลี่ยม ส่งออกเป็น GeoJSON Polygon Boundary ให้ Front-End วาดขอบเขตเตือนภัย
  • GISTDA 77 Provinces Pipeline: ประมวลผลภาพถ่ายดาวเทียมน้ำท่วมขังรายวัน แยกรายจังหวัดทั่วไทย
  • High-Speed Caching: ระบบแคชข้อมูลในหน่วยความจำ ตอบสนอง Front-End ภายใน $15-30$ms
REST API Endpoints Specification
GET /api/points
ดึงรายการจุดน้ำท่วมและระดับความเสี่ยง
POST /api/reports
ส่งรายงานเหตุน้ำท่วมด่วนจากประชาชน
GET /api/zones
ดึงอาณาเขต Polygon พื้นที่ท่วม (GeoJSON)
GET /api/gistda
ดึงชั้นข้อมูลน้ำท่วมดาวเทียม 77 จังหวัด
GET /api/stats
ดึงสถิติสรุปภาพรวมสำหรับหน้าแดชบอร์ด

ปรัชญาการออกแบบ: White Modern UI Architecture

ตัดสิ่งรบกวนสายตา (Zero Border, Zero Shadow) สร้างมิติด้วยระดับชั้นของสีพื้นผิว (Surface Layering)

1. No Border

ห้ามมีเส้นขอบกรอบตัดสายตา ใช้ความสะอาดของพื้นที่สร้างมิติ

2. No Shadow

ห้ามมีเงาดำเบลอๆ ซ้อนกัน ตัดความเทอะทะให้เบาสบายตา

3. Surface Layering

Slate 100 ➔ Pure White ➔ Slate 50 ➔ Slate 200

4. Radius Scale

องค์ประกอบนอกมนกว่าใน (20px > 14px > 10px > 8px)

กฎการสื่อสาร: Thai-First & Human Centric

ใช้ภาษาไทยเข้าใจง่าย สุภาพ • ไร้ศัพท์เทคนิคบนหน้าจอ (Controller, JSON) • ไร้วงเล็บภาษาอังกฤษ

Compact & High-Density Spacing

จัดวางข้อมูลกระชับ (Padding 10-14px, Gap 6-10px) มองเห็นภาพรวมครบถ้วนในหน้าจอเดียว
